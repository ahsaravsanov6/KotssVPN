# Архитектура VPN-платформы (v2)

## Цель рефакторинга

Было: бизнес-логика бота напрямую знала про единственный XUI-сервер
(`XUI_BASE_URL`, `XUI_SUB_DOMAIN`, `XUI_PUBLIC_KEY`... — всё в `config.py`
одним плоским списком). UUID генерировался **на устройство**, подписка
была нативной фичей 3X-UI (`/peaksub/<subId>`), добавить второй сервер
означало переписывать `xui_service.py` и backend.

Стало: 3X-UI — это **Provisioning Layer**, один из возможных бэкендов
для одного сервера. Источник истины о пользователях/устройствах — наша
БД; источник истины о списке серверов — файл `servers.yaml` (сознательно
не БД, см. раздел "Сервера — файл, не таблица" ниже). Подписка
генерируется нами, а не панелью.

```
┌─────────────────────────────────────────────────────────────┐
│  Telegram Bot            REST API (/sub/<token>, /admin/*)  │
└───────────────┬───────────────────────────┬─────────────────┘
                 │                           │
                 ▼                           ▼
┌─────────────────────────────────────────────────────────────┐
│                      Services (business logic)                │
│  UserService · DeviceService · ServerManager ·                │
│  ProvisioningService · SubscriptionService ·                  │
│  SubscriptionGenerator                                        │
└───────────────┬───────────────────┬───────────────┬─────────┘
                 │                   │               │
                 ▼                   ▼               ▼
┌───────────────────────────┐ ┌──────────────┐ ┌───────────────────────────────┐
│   Repositories (DB layer)  │ │ servers.yaml │ │  Providers (panel adapters)    │
│  UserRepository             │ │ (файл, не БД)│ │  PanelProvider (ABC)           │
│  DeviceRepository            │ └──────────────┘ │  XUIProvider (первая реализация)│
│  DeviceServerAccessRepository│                  │  ...future: MarzbanProvider    │
└───────────────┬───────────┘                    └───────────────┬───────────────┘
                 │                                                │
                 ▼                                                ▼
┌─────────────────────────────┐                  ┌───────────────────────────────┐
│   PostgreSQL / SQLite (app)  │                  │   N × 3X-UI panels (per server)│
└─────────────────────────────┘                  └───────────────────────────────┘
```

## Ключевые решения

### 1. Один UUID на устройство, размноженный на N серверов

Первая версия этой платформы делала один UUID на пользователя, общий
для всех серверов — это красиво решало задачу "одна ссылка на N
серверов", но стирало лимит устройств из исходного проекта (там лимит
считался по количеству добавленных `Device`, каждое со своим VLESS-
клиентом и `limitIp=1`).

Финальное решение: UUID снова живёт на **`Device`** (`app/db/models/device.py`),
как и в исходном проекте — просто теперь одно устройство размножается не
на единственный сервер, а на все сервера платформы через
`DeviceServerAccess` (замена `Device.vpn_email/vpn_uuid` на одном сервере
из исходной схемы). Итог:

- лимит устройств пользователя (`3 + user.extra_devices`) проверяется
  ровно так же, как раньше — по количеству строк `Device`
  (`DeviceService.add_device`, прямой аналог `/devices/add` из
  `public_html/backend/main.py`);
- `limitIp=1` на панели восстановлен — ключ конкретного устройства
  технически работает только с одного IP одновременно, как и раньше;
- перевыпуск ключа (`regenerate`) теперь снова точечный — по конкретному
  устройству, а не всем сразу;
- подписка (`/sub/<token>`) при этом остаётся ОДНОЙ ссылкой на всё —
  просто её тело содержит матрицу `устройства × сервера`: если у
  пользователя 2 устройства и 2 сервера, в подписке будет 4 строки
  `vless://`, с remark вида `"iPhone · Germany (DE)"`,
  `"iPhone · Netherlands (NL)"`, `"Android · Germany (DE)"` и т.д.

### 2. Подписка — наша, а не 3X-UI

`GET /sub/{token}`:
1. По `token` находим `User` (без раскрытия telegram_id в URL).
2. Проверяем статус подписки (`active` / `expired`).
3. Для каждого `Device` пользователя резолвим `server_id` его
   `DeviceServerAccess` в `ServerConfig` через `ServerManager.get_by_id()`
   (см. `SubscriptionService.build_subscription`) — сервер не в БД, поэтому
   этот "джойн" делается в памяти, а не SQL-запросом.
4. `SubscriptionGenerator` строит `vless://` URI для каждой пары
   (устройство, сервер) локально — из полей `ServerConfig` + `Device.uuid`.
   Никаких обращений к панели на горячем пути отдачи подписки не требуется.
5. Отдаём тело в стандартном совместимом формате (перенос-строка
   разделённый список `vless://...`, закодированный в base64) — это
   формат, который понимают Happ, v2rayNG, Nekobox, Shadowrocket,
   Streisand, sing-box (через конвертацию).

Добавление сервера пользователю = провижининг каждого его `Device` на
новом сервере. `token` и URL подписки не меняются. Добавление нового
*устройства* = новая строка в теле подписки при следующем обновлении
клиентом — сам линк тоже не меняется.

**Важно (реальный операционный пробел, а не теоретический):**
провижининг устройства на сервера происходит ТОЛЬКО в момент его
добавления, на список активных серверов на тот момент. Сервер,
добавленный в `servers.yaml` позже, сам по себе НЕ подхватывается уже
существующими устройствами — для этого нужно явно прогнать
`scripts/sync_devices_to_active_servers.py` (см. README, раздел
"После добавления сервера — обязательно докатите существующих
пользователей"). Это сознательно не сделано автоматическим (например,
через file-watcher на `servers.yaml`) — при ожидаемой частоте изменения
списка серверов (руками, редко) взрыв сложности от файлового мониторинга
не стоил бы того, что он экономит по сравнению с одной командой раз в
15-30 минут по cron.

### 3. 3X-UI — только Provisioning Layer

`PanelProvider` — абстрактный интерфейс:

```python
class PanelProvider(ABC):
    async def create_client(self, server, device) -> ProvisionResult: ...
    async def delete_client(self, server, remote_id) -> ProvisionResult: ...
    async def update_client(self, server, device, remote_id) -> ProvisionResult: ...
    async def get_client_stats(self, server, remote_id) -> ClientStats | None: ...
    async def health_check(self, server) -> HealthResult: ...
    async def fetch_technical_config(self, server) -> TechnicalConfigResult: ...
```

`XUIProvider` — единственная сегодняшняя реализация. Она ничего не
решает: не проверяет подписку, не считает лимиты устройств, не имеет
доступа к бизнес-логике. Она получает на вход `Server` (с его
собственными `panel_base_url/username/password/inbound_id`, не
глобальными настройками!) и `Device` (только `uuid` и техническое имя
клиента) и выполняет ровно то, что ей сказали — включая проверку и
принудительную фиксацию UUID после создания, если панель его
проигнорировала (см. докстринг `providers/xui/client.py`).

Добавление второй панели (например, Marzban) в будущем — это
`class MarzbanProvider(PanelProvider): ...` и один `if` в фабрике
`get_provider(server.panel_type)`. Бизнес-логика (`ProvisioningService`)
не меняется ни на строку.

#### 3.1. Технические поля сервера читаются с панели, а не вводятся руками

Ручной перенос `reality_public_key` (случайная base64-строка на ~44
символа) — самое ошибкоёмкое место при заполнении `servers.yaml`.
`fetch_technical_config()` устраняет этот шаг: парсит `streamSettings`
инбаунда (`realitySettings.serverNames`, `.settings.publicKey`,
`.shortIds`, порт) и `settings.clients[0].flow`, если хотя бы один
клиент на инбаунде уже существует. Работает только с Reality-инбаундами
(`security: reality`) — для другого транспорта возвращает понятную
ошибку, ручной ввод остаётся fallback-путём.

Ключевой инвариант: `ServerConfig.is_active` требует не только
`status == "active"`, но и `is_fully_configured` (непустые `sni` и
`reality_public_key`). Сервер, только что вписанный руками с
одними нетехническими полями (или ещё не прошедший `autofill`),
физически не может попасть в `ServerManager.list_active()` — а значит
не участвует ни в провижининге новых устройств
(`pick_servers_for_new_device`), ни в докатке существующих
(`sync_devices_to_active_servers.py`), ни в генерации подписки. Это
осознанная защита от выдачи пользователю заведомо нерабочей
`vless://`-ссылки с пустым `pbk=`.

`POST /admin/servers/{id}/autofill` — единственная точка входа: читает
через `fetch_technical_config`, затем `ServerManager.apply_technical_config`
дописывает только непустые пришедшие поля (частичный ответ панели,
например неопределённый `flow` на пустом инбаунде, не затирает то, что
уже было в файле) и сохраняет файл на диск.

### 4. Сервера — файл, не таблица БД

`.env` содержит только то, что не привязано к конкретному VPN-серверу:
строка подключения к БД платформы, `BOT_TOKEN`, `API_ADMIN_KEY`, домен
API для ссылок подписки. Параметры самих серверов (адреса, reality-ключи,
креды панелей) — это НЕ строки таблицы `servers` и НЕ переменные `.env`,
а записи отдельного YAML-файла (`SERVERS_FILE`, см. `app/servers_config.py`).

Причина: при ожидаемом масштабе (единицы, максимум десятки серверов)
полноценная реляционная таблица с Alembic-миграцией на каждое изменение
схемы — избыточная сложность. Список серверов меняется редко, вручную,
одним администратором — плоский файл проще редактировать напрямую
по SSH, не требует наката миграции ради добавления нового поля у
сервера, и целиком бэкапится/переносится одной командой `cp`.

Практические следствия этого решения:
- `Device.uuid` — обычная таблица БД (устройств может быть много, они
  создаются часто, каждое — это реальная бизнес-сущность с историей).
- `DeviceServerAccess.server_id` — обычная строка (слаг вида `"nl-1"`),
  **не внешний ключ**: такой таблицы для него не существует.
  Существование сервера с этим id на момент использования проверяется
  в рантайме через `ServerManager.get_by_id()`, а не ограничением СУБД.
  Если сервер удалён из файла, а доступы к нему в БД ещё остались — это
  не ошибка целостности, а нормальная ситуация: такие доступы просто
  перестают попадать в подписку (см. `SubscriptionService.build_subscription`).
- `ServerManager` не принимает `Session` — список серверов не участвует
  в транзакциях остальной бизнес-логики.
- Файл содержит пароли от панелей открытым текстом — путь всегда вне
  репозитория, права `chmod 600` выставляются автоматически при записи
  (`servers_config.save_all`, вызывается миграцией легаси-данных и
  `POST /admin/servers/{id}/autofill`).
- Добавление/удаление/смена статуса сервера — операция без редеплоя, но
  сознательно БЕЗ отдельного API/CLI под неё: при ожидаемых единицах
  серверов это дублировало бы то, что `nano` уже умеет. Из `/admin/servers`
  остались только три операции, каждая устраняет конкретный источник
  ошибок ручного редактирования (не про удобство записи): `GET` (список
  — падает с понятной ошибкой, если YAML синтаксически невалиден),
  `POST /{id}/health` (логин на панель без побочных эффектов — ловит
  опечатку в пароле/адресе) и `POST /{id}/autofill` (читает технические
  поля с панели вместо ручного переноса base64-ключей — см. раздел 3.1).

### 5. Разделение "чистого кода" и окружения

Репозиторий — только `app/`, `migrations/`, `scripts/`, `docs/`,
`.env.example`. Всё, что раньше подмешивалось в код по факту
(`vpn_bot.db`, `analytics.db`, `bot.log`, реальные `.env`,
сертификаты) — исключено `.gitignore` и не создаётся кодом внутри
репозитория: путь к БД, путь к логам, путь к секретам — всегда
абсолютные пути из `.env`, по умолчанию указывающие за пределы
рабочей копии репозитория (`/etc/vpn-platform/...`,
`/var/lib/vpn-platform/...`).

## Обратная совместимость и миграция

См. `migrations/migrate_from_legacy.py` и docstring внутри него. Коротко:
старая таблица `Device` (device_name, vpn_email, vpn_uuid) почти дословно
соответствует новой (`Device` + `DeviceServerAccess`) — каждое легаси-
устройство уже является полноценным VLESS-клиентом на панели, поэтому
миграция просто регистрирует его в новой БД с тем же UUID и тем же
`vpn_email` как `client_remote_id`, **без единого сетевого вызова к
панели**. Старый ключ в приложении пользователя продолжает работать без
изменений. Легаси-устройства, у которых `vpn_uuid` пуст (создание в
своё время не удалось), переносятся как непровижиненные и требуют
отдельного довыпуска.
