# Архитектура VPN-платформы (v2 + per-device нумерация)

> **Addendum (актуальное поведение):** модель "один UUID на устройство,
> реплицированный на все активные сервера" сохранена без изменений (см.
> раздел 1 ниже). Добавлено: у каждого устройства теперь есть публичный
> `device_number` — порядковый номер устройства ИМЕННО этого пользователя
> (1, 2, 3, ... и дальше при докупке доп. мест), который используется как
> имя клиента в панелях 3X-UI: `"{telegram_id}_device_{device_number}"`
> (см. `app/providers/xui/client.py::remote_id_for` и
> `app/db/models/user.py::next_device_number`). Пользователь в боте
> по-прежнему получает ОДНУ персональную ссылку НА КАЖДОЕ устройство
> (`GET /sub/{token}/{device_id}`, см. `app/api/routers/subscription.py`),
> просто эта ссылка теперь содержит записи со всех серверов, где это
> устройство провижинено.

## Цель рефакторинга

Было: бизнес-логика бота напрямую знала про единственный XUI-сервер
(`XUI_BASE_URL`, `XUI_SUB_DOMAIN`, `XUI_PUBLIC_KEY`... — всё в `config.py`
одним плоским списком). UUID генерировался **на устройство**, подписка
была нативной фичей 3X-UI (`/peaksub/<subId>`), добавить второй сервер
означало переписывать `xui_service.py` и backend.

Стало: 3X-UI — это **Provisioning Layer**, один из возможных бэкендов
для одного сервера. Источник истины о пользователях/устройствах — наша
БД; источник истины о списке серверов — файл `servers.yaml`. Подписка
генерируется нами, а не панелью, и выдаётся **на уровне устройства**:
один и тот же UUID устройства реплицируется на все активные сервера, а
персональная ссылка этого устройства (`/sub/<token>/<device_id>`) уже
включает записи со всех этих серверов сразу.


## Ключевые решения

### 1. Один UUID на устройство, размноженный на N серверов, с человекочитаемым номером

Одно устройство — одно `Device` в БД, один UUID, N записей
`DeviceServerAccess` (по одной на активный сервер). `remote_id`
(email-идентификатор клиента в 3X-UI) строится не из технического
`device.id`, а из **порядкового номера устройства этого пользователя**
(`device.device_number`), который растёт монотонно и не переиспользуется
после удаления устройства (`User.next_device_number`). Итог:

- лимит устройств пользователя (`3 + user.extra_devices`) проверяется
  так же, как раньше — по количеству строк `Device`;
- `limitIp=1` на панели восстановлен;
- перевыпуск ключа (`regenerate`) точечный — по конкретному устройству;
- в панели 3X-UI имя клиента человекочитаемо и предсказуемо:
  `367482910_device_1`, `367482910_device_2`, ... — что сильно упрощает
  ручной аудит нескольких панелей одновременно.

### 2. Подписка — по устройству, а не по всему пользователю сразу

`GET /sub/{token}/{device_id}`:
1. По `token` находим `User`.
2. Находим конкретное `Device` этого пользователя.
3. Резолвим сервера этого устройства через
   `DeviceServerAccessRepository` → `ServerManager.get_by_id()`.
4. `SubscriptionGenerator` строит `vless://` URI для каждой пары
   (это устройство, сервер) локально.
5. Отдаём тело в стандартном совместимом формате (base64 список
   `vless://...`).

`GET /sub/{token}` (без `device_id`) — подписка на все устройства сразу,
сохранена для отладки/обратной совместимости, ботом не используется.

### 3. 3X-UI — только Provisioning Layer

Без изменений — см. `app/providers/xui/client.py`. Единственное отличие
от предыдущей версии — `remote_id_for(device)` теперь строится через
`device.user.telegram_id` + `device.device_number`, а не через
`device.uuid`.

### 4. Сервера — файл, не таблица БД

Без изменений, см. `app/servers_config.py`.

### 5. Разделение "чистого кода" и окружения

Без изменений.

## Обратная совместимость и миграция

См. `migrations/migrate_from_legacy.py`. Устройствам, перенесённым из
старой `vpn_bot.db`, присваивается `device_number` по порядку их
исходного `id` внутри каждого пользователя; `User.next_device_number`
выставляется в `(количество устройств + 1)`. Их клиенты в панелях НЕ
переименовываются (остаются со старым `vpn_email`) — новый формат
`remote_id` применяется только к устройствам, добавленным после миграции.
